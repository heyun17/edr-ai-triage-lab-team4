| 2. 서버 만들기 / 공인 IP·보안 그룹 | 공인 IP 신규 할당, `edr-k8s-sg` 적용 | 할당 및 적용 확인 |
| 3. 처음 접속해 보기 | Windows PowerShell에서 SSH 개인키로 Ubuntu 접속 | `ubuntu@edr-team4` 접속 성공 |
| 3. 서버 자원 확인 | `nproc`, `free -h` | CPU 4, RAM 15Gi, 당시 사용량 470Mi, Swap 0B |
| 4. 방화벽 상태 | 가비아 보안 그룹 및 Ubuntu 서버 내부 UFW 확인 | 아래 규칙 확인 |
| 5. Day3 실습 종료 시 삭제 | 아직 수행하지 않음 | 수업 종료 시 강사 안내에 따라 정리 |

**방화벽 구분:**
- **가비아 보안 그룹 `edr-k8s-sg`:** 교안대로 22, 80, 443, 6443 등을 열어 둔 상태였음. 이 중 6443을 비롯한 일부 포트는 보안 그룹에서 `0.0.0.0/0` 허용이므로, 서버 내부 UFW 제한과 혼동하지 말 것.
- **서버 내부 UFW:** `Status: active`. 22/80/443 허용, 6443은 당시 SSH 접속자 공인 IP 한 개로 제한, k3s 내부 `10.42.0.0/16`·`10.43.0.0/16` 허용.
- `vm.max_map_count`는 초기 1048576 확인 후 `bootstrap.sh`로 262144 설정; Swap 비활성.
- SSH 22번은 아직 넓게 허용돼 있어 필요 시 접속 IP 제한을 팀과 협의할 것. 공인 IP 주소·개인키 내용·접속자 IP는 이 공개 기록에 남기지 않음.

**정리:** 사용자가 보내 준 **서버 생성/첫 SSH/방화벽 교안 사진 범위는 4번까지 실행·확인**했다. 5번 서버 삭제는 Day3 종료 작업이므로 미실행.

## 3. 추가 진행 — 팀 GitHub 인프라 1단계 (사진 바깥 범위)

아래는 사진 교안에 나온 작업이 아니라 `docs/guide/INFRA_STAGES.md`의 **2일차 인프라 1단계** 요구사항을 참고해 추가로 진행했다.

1. Ubuntu 서버에 k3s `v1.37.2+k3s1` 설치; `edr-team4` 노드 **Ready** 확인.
2. `kube-system`의 `coredns`, `metrics-server`, `traefik` 등 시스템 Pod **Running** 확인.
3. GitHub Actions `Build API image to GHCR` 성공(실행 화면 초록색 체크 확인), 컨테이너 이미지 `ghcr.io/heyun17/edr-ai-triage-lab-team4:stage1`.
4. 서버에서 GitHub 저장소 clone 후 `infra/k8s/10-namespace.yaml`, `infra/k8s/11-api.yaml` 적용: `namespace/soc`, `deployment.apps/api`, `service/api` 생성.
5. `kubectl -n soc get pods,svc`에서 API Pod **1/1 Running**, Service **ClusterIP:80** 확인.
6. 서버 내부에서 `port-forward svc/api 8000:80` 후 `GET /healthz` → `{"status":"ok","backend":"memory"}` 성공. **이 단계 API는 OpenSearch/Postgres에 연결하지 않는 메모리 모드**이며, 일반 인터넷에 API를 공개한 것은 아님.

**주의:** 인프라 1단계 전체 종료 판정은 별도이다. 강사 가이드에서 이 단계의 주 운전은 📘 문서 담당으로 지정돼 있으며, 노트북 `kubectl` 연결 확인과 팀 깨 보기/회고는 아직 확인되지 않았다. 이번 추가 배포 작업은 📘 담당 파싱·청킹(D1-7), 하이브리드 검색(D1-11), RAG 평가(D1-12)를 완료시킨 것이 아니다.
