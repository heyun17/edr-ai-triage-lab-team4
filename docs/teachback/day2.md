## 1. 🔍 조사 도구 영역 — 내가 설명할 내용

**도구와 근거**
- `get_process_tree`: `host`와 `pid`로 부모·자식 관계 추적. 다른 PC의 동일 PID를 혼동하면 안 됨.
- `get_process_activity`: 특정 프로세스의 파일·네트워크·레지스트리 등 활동 조사.
- `get_host_timeline`: 특정 시각 전후의 PC 기록을 시간순 조회.
- `get_network_connections(host, minutes)`: 목적지 IP별 연결 횟수·평균 간격 요약. WS-007 조회 결과 4개 IP, 최대 10회, `truncated=False`.
- 조회한 개별 이벤트의 `event_id`는 에이전트가 판정 근거를 실제 로그와 대조하는 데 사용함.
- 검증: `pytest tests/test_telemetry_tools.py -q` → **9 passed in 0.97s**.

**가드레일**
- G-1: 판정에 인용된 `event_id`가 실제 근거 목록에 있는지 검증.
- G-2: `malicious` 판정에는 서로 다른 근거 이벤트 2개 이상이 필요.
- 실패하면 한 번 재조사한 뒤, 여전히 근거가 불충분하면 `suspicious`로 낮추고 사람 검토 요청.

## 2. 📘 문서 검색 영역 — 내가 복습한 내용

- PDF 파싱 → 머리말·꼬리말 보정 → 청킹 → 임베딩 → OpenSearch 저장 → 하이브리드 검색(RRF).
- 검색 결과에는 `source`(출처 PDF), `page`, `score`, `category`가 있어 권고의 출처를 추적할 수 있음.
- 청크 크기 800자: **25청크, Recall@3 18/21(0.857)**.
- 청크 크기 500자: **31청크, Recall@3 18/21(0.857)**.
- 같은 검색 성능에 청크 수가 적고 09번 복잡한 표 검색 결과가 더 안정적이어서 **800자 유지**.
- 미해결: 06 스캔 PDF OCR, 07 차트 내부 숫자, 09 복잡한 표 일부 구조.

## 3. 공동 영역 — 에이전트, 체크포인트, 장애

- 악성 의심 이벤트 조사 → 근거 검증(G-1/G-2) → 권고 → 위험 조치 전 사람 승인 요청.
- PostgreSQL 체크포인트는 중단된 에이전트의 진행 지점을 저장함.
- 실제 4-5 실습: `judge` 단계 실행 중 워커 강제 삭제 → 새 워커가 체크포인트에서 재개 → `pending_approval` 확인.
- 외부 승인 API로 테스트 알림 `al-c68027792a1c`의 `approved=false` 요청 → `decision=rejected, status=completed` 확인.
- 인프라 검증: API `/readyz` 응답 `{"ready":true,"opensearch":true,"postgres":true}`; 파드 5개 정상.
- 주의: Day2의 에이전트 기준점은 `FAKE_LLM=true`, `KB_TOOLS=mock`. **실제 GPT+RAG 최종 평가로 오인하지 않음**.
