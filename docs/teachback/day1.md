## 🔍 기록 담당이 설명한 것 (D1-15 발표·시연용 정리)

> 2026-11-18 작성. 코드와 실습 결과를 바탕으로 설명하고, 서로 질문 3개씩을 실제로 주고받아 답을 확인했습니다.

**전체 흐름:** EDR 알림이 들어오면 OpenSearch의 `edr-events-*`에서 **같은 PC(`host`)와 프로세스 번호(`pid`)**로 실제 활동을 찾습니다. 조사 결과에는 `event_id`를 보존해 이후 AI 판정의 근거인지 검증할 수 있게 합니다.

| 조사 도구 | 쉬운 설명 | 입력 | 돌려주는 결과 | 실제로 확인한 예 |
|---|---|---|---|---|
| `get_process_tree(host, pid)` | **누가 이 프로그램을 실행했는가?** 부모·자식 프로세스 관계 확인 | PC 이름, PID | `process`, `ancestors`, `children`, 필요 시 `note` | `WS-006`에서 `cmd.exe`(PID 37467, `evt-00003002`) → `rundll32.exe`(PID 51765, `evt-00003003`) |
| `get_process_activity(host, pid)` | **이 프로그램이 무엇을 했는가?** 파일·통신·레지스트리·스크립트 기록 확인 | PC 이름, PID | 시간순 `events` | `evt-00003004`에서 `rundll32.exe`가 `C:\Windows\Temp\d.dmp` 파일을 생성한 기록 확인 |
| `get_host_timeline(host, around_ts, minutes)` | **그 시각 전후 PC 전체에서 무슨 일이 있었는가?** | PC 이름, 기준 시각, 전후 분 | `from`, `to`, `events`, `truncated` | `WS-006`의 `2026-11-16T09:41:43Z` 전후 1분을 조회해 공격 관련 3개 이벤트와 주변 활동 확인, `truncated=False` |

**왜 이렇게 만들었는가?**
1. 서로 다른 PC에 같은 PID가 있을 수 있어 **`host + pid`를 함께 필터링**합니다. PID만 검색하면 다른 PC 기록이 섞일 수 있습니다.
2. 프로세스의 상위 부모 이벤트가 빠졌을 때 **없는 부모를 지어내지 않고 `note`에 누락을 표시**합니다.
3. 도구 결과의 `cmdline`은 **앞 120자(`CMD_MAX=120`)**만 넘겨 LLM 입력량을 줄이되, **각 이벤트의 `event_id`는 유지**합니다.
4. `get_host_timeline`은 **최대 100건**을 반환하며, 초과하면 `truncated=True`로 제한 사실을 알립니다.
5. `pytest tests/test_telemetry_tools.py -q`에서 **8 passed**를 확인했습니다. `rundll32.exe`와 `.dmp` 생성은 의심 정황이지만 **그 기록만으로 실제 자격증명 유출까지 확정하지는 않습니다**.

**화면 설명 순서 (시연할 때):** ① `src/soc/telemetry/tools.py`의 3개 함수를 보여 줌 → ② `WS-006`의 `evt-00003002`·`evt-00003003`·`evt-00003004` 예시 설명 → ③ 테스트 `8 passed`와 `host+pid` 필터 필요성 설명.

### 🔍 고장 예상표와 실제 확인한 사례

**사례 A — 같은 PID가 다른 PC에 있는 문제 (D1-10)**
- 예상: PID만 사용하면 다른 PC의 프로세스가 같은 트리에 섞일 수 있음.
- 실제 확인: `test_process_tree_does_not_mix_hosts` 통과. `host`와 `pid`를 함께 필터링하므로 결과가 섞이지 않음.
- 배운 점: **PID는 PC 전체에서 유일한 ID가 아니므로 호스트를 반드시 확인**해야 함.
- 추가 관찰: 상위 부모 생성 이벤트가 없으면 없는 관계를 만들어내지 않고 누락을 안내함.

**사례 B — 인프라 0-2 Docker Compose 포트 충돌 (실제 장애 복구)**
- 증상: `Bind for 127.0.0.1:5432 failed: port is already allocated`
- 원인: Postgres가 5432 포트를 사용하는데 OpenSearch까지 호스트 5432에 매핑되어 충돌.
- 조치: OpenSearch의 포트를 `127.0.0.1:9200:9200`으로 복구해 재실행, Started 확인.
- 다음에 처음 확인할 명령: `docker compose ps -a`
- 근거: [`docs/RUNBOOK.md` 0-2 기록](../RUNBOOK.md). 복구 시간과 출제자 회고는 RUNBOOK에 아직 빈칸이므로 실제 확인 후 보완 필요.
