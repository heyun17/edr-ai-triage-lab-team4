## 🔍 기록 담당이 설명할 것

1. **데이터 수집과 근거 추적:** 프로세스·파일·통신 로그를 OpenSearch에 적재하고, `host`와 `pid`를 함께 조회한다. `event_id`를 보존해 LLM 판정이 실제로 확인한 증거에 근거하는지 검사한다.
2. **D3-5 개선:** 정상 IT 스크립트의 부모 프로세스 `parent_name`이 도구 요약에서 빠진 탓에 가짜 LLM이 12건 중 2건을 잘못 판정했다. `summarize()`에 해당 필드를 유지하도록 바꾸고 동일 12건으로 검증해 **10/12 → 12/12**(FakeLLM) 확인. 개선 이미지 `a8dc79a`를 Worker에 롤아웃했다.
3. **인프라와 장애:** Kubernetes의 Deployment/StatefulSet/PVC를 구성하고, Job URL 오타(실패→복구), 신규 파드 즉시 종료(구버전 유지→롤백), Service selector 503(EndpointSlice→복구)을 다뤘다.
4. **CI/CD 경계:** GitHub Actions는 테스트·Docker 빌드·GHCR 푸시까지 자동이고, k3s 이미지 반영과 롤백은 수동이다.

### 강사 질문 대비 (실제 타인 질문이 아닌 개인 연습)

**Q1. 같은 PID로 조회하면 왜 위험한가?**  
A. 다른 PC에서 같은 PID가 재사용될 수 있으므로 `host+pid`를 같이 조건으로 걸어야 다른 PC 기록이 섞이지 않는다.

**Q2. 새 이미지가 Error인데 API가 어떻게 살아 있었나?**  
A. 테스트용 배포의 `maxUnavailable: 0` 때문에 기존 정상 파드가 남았다. 새 파드 로그를 확인한 뒤 `rollout undo`로 이전 버전을 복구했다.

**Q3. FakeLLM 100%를 실서비스 정확도라고 해도 되나?**  
A. 안 된다. 12개 합성 알림에서의 회귀 테스트 성적이며 실제 GPT 모델·운영 데이터 성능은 미검증이다.

## 📘 문서 담당 영역을 내가 설명할 수 있는 내용

- 9개 PDF에서 OCR/2단 레이아웃/복잡 표 등의 파싱 난이도가 달랐다. 기본 KB는 25청크였고, 06번 스캔 PDF는 0청크였다.
- D3-6 개인 실습으로 06번 PDF에 `ocr_only`를 적용하면 요소 34개/청크 1개였으나 한국어 인식이 심하게 깨졌다.
- 직접 `300dpi, tesseract kor+eng --psm 6`로 594자와 k10의 정답 ‘세 번’을 추출해 **실험 KB 26청크 중 1개만 재임베딩**했다.
- 수정된 실험 인덱스에서 Keyword Recall@3 **19/21→20/21**, Vector/Hybrid **18/21→19/21** 확인. 운영 KB와 영구 ingest 코드는 변경하지 않았다.

### 강사 질문 대비 (실제 타인 질문이 아닌 개인 연습)

**Q1. OCR로 청크가 생성되면 RAG 정답이 맞다는 뜻인가?**  
A. 아니다. 최초 OCR은 심하게 오인식됐고 Recall@3는 정답 문서가 상위 3개에 있는지를 재는 지표다. PDF06은 추출 본문에 ‘세 번’이 있는지도 별도 확인했다.

**Q2. 가중치 100:1로 RRF를 바꾸지 않은 이유는?**  
A. 기존 평가셋에서는 BM25 단독과 20/21로 동률이었고 독립 데이터 검증도 없기 때문이다. 과도한 키워드 편향을 정식 운영에 적용하지 않았다.

**Q3. PDF 처리 이미지와 일반 API 이미지를 분리한 이유는?**  
A. Unstructured OCR·Tesseract·Torch 등이 무거워서 PDF 적재만 별도 Job/이미지로 실행해 앱 컨테이너의 크기와 의존성을 분리했다.
